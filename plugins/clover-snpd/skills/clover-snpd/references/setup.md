# Clover SNPD — Setup & Connection

## Dependencies

```bash
npm install remote-pay-cloud ws xmlhttprequest-ssl
```

- `remote-pay-cloud@4.1.2` — Clover JavaScript SDK
- `ws@8+` — WebSocket implementation for Node.js
- `xmlhttprequest-ssl` — XHR implementation required by the SDK

## Device Setup

### Install SNPD on the Clover device
1. On device home screen: tap **More Tools**
2. Search: **Secure Network Pay Display**
3. Tap result -> **Connect** -> **Connect**

### Configure SNPD settings (on device)
Open Network Pay Display app -> menu icon -> Settings:

| Setting | Value |
|---|---|
| Server is Secured | **Unchecked** (ws:// — no certificate needed) |
| Server Port | 12345 (default) |
| Enable Ping | Checked |

**Server is Secured must be OFF.** Posberry runs this way in all installations. Avoids all CA certificate complexity on the POS server.

### Get the device IP
The main screen of the Network Pay Display app shows the endpoint, e.g.: `ws://192.168.1.50:12345/remote_pay`

## CRITICAL: Node.js WebSocket Implementation

The SDK requires a `CloverWebSocketInterface` instance — NOT a raw `ws` WebSocket.
The `webSocketFactoryFunction` must return a class that extends `CloverWebSocketInterface`.

**Create `clover-websocket.ts`:**

```typescript
import * as WebSocket from 'ws';

const { CloverWebSocketInterface } = require(
  'remote-pay-cloud/dist/com/clover/websocket/CloverWebSocketInterface'
);

class NodeWebSocketImpl extends CloverWebSocketInterface {
  createWebSocket(endpoint: string): any {
    // Pass NO extra arguments — any extra arg corrupts the WebSocket upgrade handshake
    return new (WebSocket as any)(endpoint);
  }

  sendPong(): this { return this; }
  sendPing(): this { return this; }

  static createInstance(endpoint: string): NodeWebSocketImpl {
    return new (NodeWebSocketImpl as any)(endpoint);
  }
}

export const nodeWebSocketFactory = NodeWebSocketImpl.createInstance;
```

**Why:** The SDK's `CloverWebSocketClient` calls methods like `sendClose()`, `sendText()`, `addListener()` on the socket — methods that don't exist on a raw `ws` WebSocket. Extending `CloverWebSocketInterface` provides all of them.

**Common mistake:** Passing `{ rejectUnauthorized: false }` as the second arg to `new WebSocket()` — this gets interpreted as the WebSocket subprotocol and corrupts the HTTP upgrade request, causing a connection error.

## Connection Configuration

Use `WebSocketPairedCloverDeviceConfiguration` (NOT `WebSocketCloverDeviceConfiguration`).
Use `new CloverConnector(config)` directly (NOT the factory builder).

```typescript
import * as clover from 'remote-pay-cloud';
import { nodeWebSocketFactory } from './clover-websocket';

const imageUtil = {
  getImage: (_url: string, cb: (img: any) => void) => cb(null),
};

const deviceConfig = new (clover as any).WebSocketPairedCloverDeviceConfiguration(
  `ws://${deviceIp}:12345/remote_pay`,  // endpoint
  RAID,                                  // applicationId — from Clover Developer Dashboard
  posName,                               // e.g. 'TotemFortin'
  serialNumber,                          // free identifier, e.g. `TOTEM-${terminal.id}`
  pairingToken,                          // null on first pairing, saved token on reconnect
  (code: string) => { /* show code to operator */ },
  async (token: string) => { /* save token to DB */ },
  nodeWebSocketFactory,                  // MUST be NodeWebSocketImpl.createInstance
  imageUtil,
);

const connector = new (clover as any).CloverConnector(deviceConfig);
connector.addCloverConnectorListener(listener as any);
connector.initializeConnection();
```

## Pairing Flow (Real-world, verified)

**First connection:**
1. POS sends `initializeConnection()`
2. **Clover terminal prompts the operator for the admin key** (on the device screen)
3. Operator enters admin key on the terminal
4. SDK fires `onPairingCode(code)` — **show this code in the POS UI**
5. Operator enters the pairing code on the terminal
6. SDK fires `onPairingSuccess(authToken)` — **save this token to DB**

**Subsequent connections:**
- Pass saved `pairingAuthToken` to config → reconnects automatically, no pairing needed
- Token validity is configurable on the device (number of days)

## RAID Setup

The RAID is auto-generated by the Clover Global Developer Dashboard when creating a semi-integrated app.

Dashboard path: App Settings → App Type section → **Remote App identifier (RAID)**

Format example: `XXXXXXXXXXXXX.XXXXXXXXXXXXX` (two alphanumeric blocks separated by a dot)

Required permissions in the dashboard:
- Merchant: READ
- Payments: READ + WRITE
- Orders: READ + WRITE

Do NOT enable: Customers, Employees, Inventory, Ecommerce (not needed for SNPD).

## Device IP Storage

Store the device IP on the `Terminal` row (`Terminal.cloverIp`), one row per Clover device, not in env vars. Operators change it from the terminals CRUD in the admin UI without restarting the server. The same row holds `cloverRaid` and `cloverPairingToken`.

```typescript
const terminal = await prisma.terminal.findFirst({
  where: { status: 'active', cloverIp: { not: null } },
});
const endpoint = `ws://${terminal.cloverIp}:12345/remote_pay`;
```

## Multi-POS / Multiple Totems

SNPD supports **multiple simultaneous POS connections** to the same terminal. If two totems send a `SaleRequest` at the same time, the Clover queues them — the second waits until the first completes. No coordination needed on the POS side.

## Environment Variables

```env
CLOVER_RAID=<your RAID>          # from Clover dashboard; copied to Terminal.cloverRaid when a terminal is created, and used as fallback
CLOVER_POS_NAME=TotemFortin      # optional, defaults to 'TotemFortin'
# No device IP or serial in env: the IP is Terminal.cloverIp (admin UI) and the serial is `TOTEM-${terminal.id}`
# The scheme is always ws:// (no TLS) — there is no secure toggle
```
